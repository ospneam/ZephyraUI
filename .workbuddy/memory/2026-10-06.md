### 关键发现（按严重度）

1. **四边形没有 AA 余量 → 所有边缘是硬边**（已确认，非猜测）

## 架构决策：效果器层与 base 并列（用户拍板）

用户提出：**效果器放core，只有必须与系统底层操作的放 base，其他全在 core**。
问清后的最终结构（用户明确表述）：

- **资源管理器分上下两层**：下层负责与系统直接沟通，上层不与系统直接沟通，
  **上层允许开发者直接定制**。
- **开发者可整体替换，也可部分覆盖**：下层提供 API，上层实现具体算法。
- `zephyra-gpu` **升格为效果器层**（与 base 并列）—— 理由：它零GPU 依赖、
  `forbidunsafe`、纯 CPU 数据，本就不属于系统适配层。

### Skia 的先例（已核实 D:\code\skia-main）

Skia 把 `src/effects` 与 `src/core` 放在**并列层**，不是 core 内部；
`include/effects` 依赖 `//src/core`，而 `include/core` **零引用** effects
（`include/effects/BUILD.bazel:43` 与 grep 零命中）。

结论：**描述层放core，执行层留 base**。Skia 从不把执行放 core——
`Blur` 在 core 只是描述，真正跑 pass 的在 `src/gpu/ganesh/ops/`。

判据定为**「能不能在无 GPU 机器上写单测」**。

## 已完成：修复四边形 AA 硬边（任务 #1，验证通过）

病因：`quad.rs::Vertex::quad` 让四边形恰好等于矩形 ⇒ `d ≤ 0` 恒成立，
`d ∈ (0, 0.75]` 那半边过渡带被裁掉。

修法（**`half_size` 与顶点布局都没变，HLSL 的 SDF 也无需改**）：
- 新增 `quad::AA_BAND = 0.75`，与 HLSL 的 `float px` 绑定为同一常量
- `Vertex::quad`：SDF 类别几何向外扩 `AA_BAND`，`half_size = (尺寸 + 2*pad)/2`。
  **字形/图像不扩**（位图自带AA，扩了会把边角啃掉/把 uv 拉出图块）
- 裁剪后**收缩半个 AA 带**（`shrink()`），否则裁剪线处会有一圈没裁干净的发白边
- `sdf_coverage` 的 `AA` 常量改为引用 `quad::AA_BAND`，避免两处分叉

### ⚠ 外扩引出的新缺陷（必须一起改，否则描边多一圈实色）

描边分支的 `sa = smoothstep(-width-px, -width+px, d)` 在 `d > 0` 时**饱和为 1**。
外扩后 `d ∈ (0, 0.75]` 那段会变成一圈**没有抗锯齿的实色**，症状是「描边比设定值
粗一圈」。修法：`sa *= (1.0 - smoothstep(-px, px, d))`，两个后端的 HLSL 都改了。

## 已完成：图集淘汰策略抽成可替换 trait（验证通过）

用户拍板「无 GPU 资源预算，做这个」→ 范围收敛为 CPU 侧资源管理。

### ⚠ 先更正我先前审计的两处错误结论

1. **「图集无 LRU 淘汰」是错的** —— `zephyra/src/text/atlas.rs` 早已实现
   `make_room` / `fits` / `rebuild` 三件套，且有 6 条测试覆盖（淘汰顺序、幸存者 uv
   不重叠、无残墨、revision 前进、缓存命中不淘汰、超大字形返回 None）。
   错因：当时只看了 `zephyra-fx/src/texture.rs` 的 `TextureNames`，没打开 core 里
   真正的图集。
2. **「顶点缓冲无复用」也是错的** —— D3D11 `renderer.rs:465` 与
   D3D12 `renderer.rs:841` 都有 `next_power_of_two` 按需扩容。

真实缺口只有一条：**淘汰策略写死在 `GlyphAtlas` 私有方法里，开发者无法替换**。
所以 `crates/base/README.md` 里「图集满了只能整体失效」这句也是错的，已改。

### 契约设计（core，零依赖）

```
trait EvictionPolicy {
    fn evict(&self, entries: &[EntryInfo], need: (u32,u32), side: u32) -> Option<EvictPlan>;
}
```

- `GlyphKey` 从私有 type alias 提成公开 struct（策略必须能指名条目）。
- `side` **显式传参**而非读全局 `ATLAS_SIZE`：`with_size` 能缩小图集，
  策略若按 1024 算就会判错。
- `LruEviction` 是默认实现（丢最久未用 + 高度降序重排）。

### 关键设计：消灭 `fits`/`rebuild` 排序漂移

原先 `fits`（干跑）与 `rebuild`（落盘）**各写一遍排序**，靠注释警告保持一致。
漂移后果极恶劣：判得下却放不下，而那时画布**已清空** → 图集一片空白且零报错。

现在 `EvictPlan::survivors` 携带的就是**重排顺序本身**，两处共用同一顺序源，
漂移在类型层面不可能发生。图集还在清空前**独立复验**一次（策略是外部代码，
可能算错；那时宁可放弃淘汰，也不能拿已清空的画布去赌）。

### 顺带修掉一个真实 bug：空白条目被静默丢弃

`rebuild` 只保留策略提名的 `survivors`，而空白字形（空格）不占画布、被
`LruEviction` 排除在名单外 → **重排后全部消失**。症状极隐蔽：空格相关的排版度量
悄悄变了（空白的 `offset` 决定光标推进）。修法：`rebuild` 末尾无条件把
`padded_size == (0,0)` 的条目捞回表里。

另外 `padded_size` 原来给空白返回 `(2,2)`（`2 × GLYPH_PADDING`），已改为 `(0,0)`
—— 它同时喂给策略的 `padded` 与落盘的 `place`，给错就又是「判得下、放不下」。

### 宿主侧入口

`TextStack::set_atlas_policy` / `with_atlas_policy` —— 宿主实际持有 `TextStack`
而非 `GlyphAtlas`，没这一层 trait 就是够不着的契约。换策略**不重建图集**，
新策略从下一次放不下时生效（换策略本身不该让幸存者 uv 全部失效）。

### 写测试的教训（这次踩了4 次）

- `Cell` **不共享**。策略被 move 进 `Box<dyn>` 后，外部拿独立 `Cell` 副本读永远是 0
  —— 断言"策略没被调用"，而调用其实发生了。必须用 `Rc<Cell<_>>`。
- 凑"恰好装满"的图集边长极易算错：32×32 下 `22+10=32` 恰好放得下 ⇒ 以为会触发
  淘汰其实没触发；28×28 下换行后不够放第四个 ⇒ 策略正确返回 `None` 而测试误判成
  「图集没采纳策略」。**两次都是前提算错，不是实现问题。**
- 淘汰只在**放不下**时被触发，所以「某条目不该被丢」这类断言要小心：最后几个
  字形可能是在最后一次淘汰**之后**才插入的，它们留在图集里完全正常。
- 判「顺序是否被照搬」用 **x 坐标**而非 y：同高的字形必然同行，y 全相同。

### ⚠ 设计上推翻了原提案：`PushLayer`/`PopLayer` 配对命令是错的

核实Skia 源码后确认三条硬事实：

1. **`DisplayList` 构造时即按 `(layer, z, order)` 稳定排序**（`paint.rs:16-19`），
   配对标记靠"在有序流里前后夹住内容"生效，排序会把中间内容插到别的 layer 上 ——
   配对当场失效且**零报错**。
   现有 `PushClip`/`PopClip` 之所以没出事，是因为它们**零生产者**（全仓只有定义处
   与 fx 的消费处）。这个坑已在 `Command` 的文档注释里钉住。
2. **Skia 压根不用配对命令**：滤镜挂 `SkPaint`，离屏由
   `SkCanvas::aboutToDraw` → `AutoLayerForImageFilter`（`SkCanvasPriv.h:129`）
   在回放时按需自动开，`getImageFilter()` 非空才 `addImageFilterLayer`
   （`SkCanvasPriv.cpp:234`）。
3. **离屏边界是算出来的**：`addLayer` 走 `paint.computeFastBounds(drawBounds)`
   （`SkCanvasPriv.cpp:308`），由滤镜贡献 outset。

### 修掉的实现 bug（测试逼出来的，非测试算错）

`DropShadow` 的 outset 我最初写成"只有投影方向扩"，导致 `left = r - offset.x.min(0)`
恒为 `r`，离屏矩形被整体平移（`bounds.x = -6`），症状是元素左上角出现一段未渲染空白
且不报错。正确语义：**模糊半径四边都扩**，offset 只是平移 ⇒

## geom 三角化：扫线移植失败回滚 + 失败用例的真实根因定位

### 结论一：不是 base 的问题

两个失败用例（`多个孔都要被挖掉`、`闭合描边三角化后面积等于环带面积`）**全部在core 层**，
与 base 无关，硬证据三条：

1. `cargo tree -p zephyra` 输出**只有自身一行** —— core 零依赖，物理上不可能引用 base。
2. `geom_tests.rs` 里 `zephyra-fx / dcomp / winit / d3d / gpu` **零命中**（唯一一处"GPU"
   出现在第59 行注释里，说明覆盖率函数与GPU 光栅一致）。
3. `Partial` 错误由 `tessellate.rs:205` 的 `degraded` 标志产生，纯CPU 判定。

base 侧确有`Command::Path` 未接通（`quad.rs:525` 是 `skipped += 1`）与
`MultisampleEnable: 0`（winit 与 d3d12 两处），但那是**独立的待办**，不是这两个失败的原因。

### 结论二：扫线移植（GrTriangulator）已回滚

- 回滚点：`/tmp/tessellate_before_sweep.rs`，回滚后 `cargo test -p zephyra geom`
  = **32 passed / 2 failed**，与改动前一致。
- 失败根因（写在这里避免重走）：`Poly::addEdge` 有**四条分支**，漏了最后一条
  `else` 里的 **inner edge**（`allocateEdge(fTail->fLastEdge->fBottom, e->fBottom, kInner)`）。
  它是把左右两段接成完整边界的**唯一机制**，`fPartner` 也在这一带。
  漏掉后每段 `MonotonePoly` 只有 1 条边 → `emitMonotonePoly` 的 chain 只有 2 个顶点
  → `n < 3` 全被跳过 → 连三角形都产不出。
- **方法论教训**：把 `Poly{fHead,fTail,MonotonePoly}` 压成 `Vec<MonotonePoly>` 时，
  自以为"等价"的简化恰好丢了承重部分。移植指针链表算法**不能压缩结构**。
- 已用 Python 逐行复刻验证过：原版逻辑在简化前提下同样输出 0，确认不是 Rust 侧问题。

### 结论三：两个失败用例的真实根因（与"多孔"无关）

用逐步排除法定位，**此前的判断（"多孔无解"）是错的**：

**`闭合描边三角化后面积等于环带面积`** —— 根因是 `stroke_outline` 产出的**内轮廓几何自相矛盾**：
```
ring1: v0=(0,1) v1=(1,1) v2=(1,10) v3=(1,9) v4=(10,9) v5=(9,9) v6=(9,0) v7=(9,1)
边1: (1,1)→(1,10) 长 9← 沿 y 正向走完
边2: (1,10)→(1,9) 长 1  ← 沿 y **负向**退回 1
边3: (1,9)→(10,9) 长 9   ← 紧接着横向往右
```
v1→v2→v3 在 x=1 这条线上**先向上再向下折返**，是一个 1 单位的" spike"。
内轮廓**单独** triangulate 直接 `ERR 找不到可切的耳`（连 4 个顶点都不给）。
对照实验证实：外轮廓 8 点斜角 + 内 4 点方 → **OK 12 三角形**；
外 4 点方 + 内 8 点斜角 → **ERR**。变量是内轮廓形状，不是点数、不是多孔、不是斜角深度。

**`多个孔都要被挖掉`** —— 环带用同一个`stroke_outline`，同一个 spike 缺陷；
两孔情形另外还叠加桥接落点问题。18 个三角形里出现大量重复三元组。

**修法方向**：`stroke_outline` 闭合路径的内缩环生成有bug（应保留 4 个角点、
每边只缩进 hw，不该产生折返 spike），修它可同时解掉环带用例并缩小多孔失败面。

## stroke_outline 尖刺修复 + 增量耳切去重（geom 从 32/2 → 273/1）

### 修复一：`stroke_outline` 闭合路径的零面积尖刺（真实几何缺陷）

**症状**：`闭合描边三角化后面积等于环带面积` 失败，报`Partial`。

**根因**：`append_join` 在 miter 合格时输出「尖角 + `next_start`」两点。而凸角处
`next_start`（出边偏移线自己的端点）落在尖角**之前**，环于是退回去一截形成
**面积为零的尖刺**。实测内轮廓：

```
旧: (0,1)(1,1)(1,10)(1,9)(10,9)(9,9)(9,0)(9,1)   ← v1→v2→v3 在 x=1 上折返
新: (1,1)(9,1)(9,9)(1,9)                          ← 干净的 8×8 四点方
```

尖刺在非零填充下不算错（环绕数相消），但它是**自交退化多边形**，耳测试的
「三角形内不含其他顶点」会被尖刺的重复顶点否掉→ `找不到可切的耳`。内轮廓
只有 8 个点、单个孔，**单独**三角化就失败。

**改法**：miter 合格时**只输出尖角**；bevel / 超限 / 平行才输出
`prev_end + next_start`。相邻接头之间是直线，不需要补点。
同时把 `offset_side` 从「逐点输出偏移点」改为「按顶点输出接头」，
`offset_of(i-1)` 改为 `line_end_at(i)`（入边偏移线的**终点**，不是起点）。

**验证**：内轮廓 8 点→ 4 点，环带解析面积 **精确 80.0000**。

### 修复二：网格采样覆盖率当精确判据（测试缺陷）

环带覆盖率实测 81.28、断言容差 0.6。查证：`Σ|三角形面积|` = **80.0000**，
覆盖率随网格加密是79.03 / 81.28 / 79.60 / 79.88 / 80.16 —— **不单调收敛**，
它量化的是采样栅格与边界的对齐，不是几何误差（对轴对齐矩形是 O(周长/n) 抖动）。

改用`mesh_area()`（解析面积）断言，容差 0.01；采样覆盖率降级为粗筛，容差 2.0。

### 修复三：增量耳切产出重复三角形

**症状**：双孔用例 18 个三角形，`Σ|面积|` = 474 而正确值 268。
探针显示 **#6..#11 与 #12..#17 逐个完全相同** —— 两轮耳切切了同一批耳。

**根因**：`stop_early` 的语义是「切到 `remaining == 4` 才停」并返回剩余环。
那个剩余环的顶点**仍与已切掉的三角形共享边界**，下一轮从它出发必然再切一遍。

**改法**：增量模式**一轮只切一个耳**就返回剩余环（`single_shot`），
`must_stop`（`remaining <= 4`）仍作为保底。结果 18 → 5 个三角形，重复消除。

**但这只是止损不是解决**：切完只剩 5 个三角形、第二个孔桥接仍失败 → 仍是 `Partial`。
见下条。

### 剩余失败：`多个孔都要被挖掉`（结构性，需换算法）

穷举确认**与孔间距无关**：相邻孔、远离孔、三孔、宽外框（60×10）全部失败。
根因仍是桥接法的固有局限——第一个孔的桥把环改写成自交形状后，第二个孔的
射线落点必然落进那条窄缝，`bridge_hole` 的可见性判据全部否掉。

即之前穷举「40 种(落点₁, 落点₂)组合全失败」的结论。**桥接法在多孔上无解**，
必须换结构（earcut 链表式/ 扫线分解），不是调参能解决的。

## MSAA 与渲染管线深度优化（本轮）

### MSAA 开启（Task #21）
- 后缓冲**永远单采样**（DXGI 无此API），所以必须自建多重采样纹理 + `ResolveSubresource`
- **两处必须同时改**：`MultisampleEnable`/`SampleDesc` 与多重采样 RTV。只改一个必黑屏
- D3D12：采样数经 `Swapchain::samples()` 传给 `Renderer::new`（PSO 建好即固定，顺序不可反）
- D3D11：`Renderer::new` 与 `Surface::new` 各自调 `surface::msaa_samples(device)` 同一函数
- ⚠ 实测坑：MSAA 纹理必须给 `D3D12_RESOURCE_FLAG_ALLOW_RENDER_TARGET`，否则
  `CreateCommittedResource` 返 `E_INVALIDARG`——**与采样数无关**（1×/2×/4×/8× 全挂），
  症状看起来像"设备不支持 MSAA"。且缺该 flag 时不能用 `create_resource`
  （它只在有 flag 时给同格式 clear value）
- 4× 而非 8×：UI 帧时间几乎全在填充率上
- 真机验证：`swapchain_draw` 像素覆盖 63.5% ≥ 几何要求 62.1%

### 性能：数据推翻了我的估算（Task #22）
基线 1019 µs → **510 µs**（2.0×），分配 309 KB/帧 → 116 KB/帧。

| 阶段 | 之前 | 之后 |
|---|---|---|
| paint | 603 µs | **103 µs** |
| expand | 263 µs | 261 µs |
| view | 112 µs | 112 µs |

**根因：图标三角化 50 µs × 8 个 = 400 µs**（占 paint 的 66%）。

修法：`IconSet` 上加几何缓存，键 =（图标数据地址, 矩形四位模式）。

# 文档

两份文档，**读者不同**。先确认你要的是哪一份，再往下点。

| | [`developer/`](developer/README.md) | [`dev-log/`](dev-log/README.md) |
|---|---|---|
| 给谁 | **外部使用者** | **内部**（本仓开发者、未来的自己） |
| 内容 | 怎么用、为什么这么设计 | 踩过什么坑、**排除过什么** |
| 变化频率 | 跟着功能走 | 跟着事故走，只增不改 |
| 可信度 | 规范，说的是「应该」 | 记录，说的是「实际发生过」 |

## 为什么必须分开

`dev-log/` 里最有价值的东西是**失败的假设**。

比如 GPU 挂死那次，先后猜错了四轮：命令列表、命令分配器、MSAA 纹理、`ResizeBuffers`。
这四轮「排除掉」的知识在任何规范文档里都写不出来——它们不是「应该怎么做」，是
「不要再去试了」。

把它们和用户文档混在一起，用户要翻规范时会撞见一堆他不关心的失败路径；反过来，如果只
写规范，那些坑会被**重新踩一遍**，因为没人记得试过什么。

## 写规范时的一条纪律

> 写进注释和文档的每个数字，都要有一次**实测**背书。

本仓因此有两条「实测无收益所以没做」的记录留在代码注释里——它们的价值恰恰在于**说明
那条路已经走过了**。

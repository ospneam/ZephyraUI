# 响应式布局与触控适配 —— 依据与实现口径

> 本文件是**实现前的依据**，不是实现后的说明。里面每个数字都带出处，
> 改动这些数字前先回查原文。
>
> 出处（2026-10 查，均 `zh-cn`）：
> - 断点：<https://learn.microsoft.com/zh-cn/windows/apps/design/layout/screen-sizes-and-breakpoints-for-responsive-design>
> - 响应式技术：<https://learn.microsoft.com/zh-cn/windows/apps/design/layout/responsive-design>
> - 触控交互与命中目标：<https://learn.microsoft.com/zh-cn/windows/apps/design/input/touch-interactions>
> - `AdaptiveTrigger`：<https://learn.microsoft.com/zh-cn/uwp/api/windows.ui.xaml.adaptivetrigger.minwindowwidth>

## 1. 断点（官方三个尺寸类别）

官方措辞：「与其针对每种屏幕尺寸优化界面，不如围绕几个称为 *断点* 的关键宽度类别进行设计」。

| 尺寸类别 | 断点 | 官方典型窗口大小 |
|---|---|---|
| 小（Small） | **最大可达 640 px** | 480x854、540x960 |
| 中（Medium） | **641 – 1007 px** | 960x540 |
| 大（Large） | **1008 px 及以上** | 1024x640、1366x768、1920x1080 |

官方还有一句关键的判据口径：

> 在针对特定断点进行设计时，应以**应用可用的屏幕空间（即应用窗口）**为依据，
> 而不是以物理屏幕尺寸为依据。

所以本仓按**窗口客户区**判，不按显示器判。

## 2. 单位：有效像素（epx）

> 有效像素（epx）是一种虚拟度量单位，用于表示布局尺寸和间距，与屏幕密度无关。
> （在我们的指南中，epx、ep 和 px 可以互换使用。）

`AdaptiveTrigger.MinWindowWidth` 的官方定义同样写着：

> The minimum window width (**in effective pixels**) at which the VisualState
> should be applied.

⇒ **断点判定必须用有效像素**，不是物理像素。本机 scale = 1.25，所以
1400 物理 px 宽 = **1120 epx**（大）；800 物理 px 宽 = **640 epx**（正好落在
小/中边界上）。按物理像素判会整体错一档。

## 3. UI 尺寸取 4 epx 的倍数

> UI 元素的大小、边距和位置应始终位于 XAML 应用中 **4 个 epx 的倍数**中。
> XAML 可按 100%、125%、150%、175%、200%、225%、250%、300%、350%、400% 缩放。
> 基单位为 4，因为它以整数的形式缩放到这些高原（例如，4 × 125% = 5）。
> 使用 4 的倍数可以使所有 UI 元素对齐到整数像素，并确保边缘清晰锐利。
> （文本没有此要求。）

本机 scale 1.25 正是列出来的那一档，所以这条在本机**直接可见**：
非 4 倍数的边距会被缩放成小数像素，边缘发虚。

## 4. 触控：最小命中目标

官方原文（`touch-interactions` 的「命中目标」节）：

> **可触摸的**：我们将「可触摸」定义为最小 **40 x 40 epx**（即使视觉对象较小），
> 或 **32 epx 高**（如果宽度至少为 **120 epx**）。
>
> **触摸优化**：对于触摸优化的 UI，请考虑将触控目标的大小增加到 **44 x 44 epx**，
> 触控目标之间至少有 **4 epx** 的可见空间。

取用：

| 场景 | 判据 | 本仓落地 |
|---|---|---|
| 通用下限 | 40 × 40 epx | 所有可交互元素的热区不小于 40（本仓基准，见 §5） |
| 宽条目标 | 高 32 epx，宽 ≥ 120 epx | 导航项这类宽条形可用 32 高，但宽必须 ≥ 120 |
| 触摸优化 | 44 × 44 epx | 触摸态下放大到 44 |
| 目标间距 | ≥ 4 epx 可见空间 | 交互项之间的 spacing 不小于 4 |

## 5. 本仓的单位基准（**一处记账，影响全部解释**）

`zephyra-core` 的布局单位是「1 单位」，宿主管它叫 DIP。当前实现把**物理像素**
直接交给 core 当视口（`HostWindow::client_size()` → `window.inner_size()`），
于是本仓现在的实际基准是：

> **1 布局单位 = 1 物理像素**

这与 §2 的 epx 语义在 scale ≠ 100% 时不一致：1.25 缩放下，样式表里写 40 的
元素视觉上只有 32 epx，**低于官方「可触摸」下限**。

本轮的处理（**不触碰全局基准**，因为那会让全部视觉验收数字作废）：

- 断点判定按**有效像素**（`物理 / scale`）—— 这是 §2 的硬要求，且只影响
  「走哪套布局」，不影响任何外观值；
- 触控目标按 `40 × scale` 给**物理像素**，从而视觉上是 40 epx。
  这一项只在**触摸路径**上放大，鼠标路径不变。

⚠️ 把基准从「物理像素」改成「有效像素」是独立的一轮工作（会改变全部视觉尺寸），
已记账在 `REWRITE.md`，不与响应式混做。两者不能同时改，否则一次改动同时动了
「哪套布局」和「布局有多大」，出问题无法归因。

## 6. 实现手段：官方六种技术里选哪些

官方 `responsive-design` 页列出六种：重新定位 / 调整大小 / 重新排列 / 显示隐藏 /
重新构建 / 自适应布局。最后一条的官方描述正是本轮的形状：

> 自适应布局类似于响应式布局，但完全取代了基于其呈现格式的 UI。
> 自适应设计具有多个固定布局大小，并触发页面根据可用空间加载给定布局。
> 使用这种技术，可以针对特定断点来切换用户界面。……瞬态 UI（导航窗格及其精简版）
> 适用于较小的屏幕，但在较大屏幕上，最好选择使用选项卡。

本仓取四種，理由各不同：

| 技术 | 本仓用在哪 | 为什么选它 |
|---|---|---|
| **自适应布局** | 小断点折叠导航 | 官方举的例子就是 NavigationView 的 pane 精简版 |
| **重新排列（Reflow）** | 卡片网格列数随宽度变 | core 无 Grid/星号，列数只能在视图层按可用宽度算 |
| **调整大小（Resize）** | banner 高度、链接卡排布 | 用分类名切样式变体，值仍在 zstyle |
| **显示/隐藏（Reveal/Hide）** | 小断点隐藏次要元数据 | 比「挤成一团」诚实 |

`重新定位` 与 `重新构建` 本轮**不做**：前者需要绝对定位能力，后者需要拆分整个
外壳骨架，而 core 没有对应原语。不做不等于漏 —— 记账在这里。

## 7. 断点在哪一层表达（关键设计决定）

zstyle **没有** media query，所以断点不可能写在样式表里。但这不等于要把颜色/尺寸
搬进源码 —— 那会破坏本仓「源码零外观」的规矩（`tests/gates.rs` 第一条）。

解法是把两种决策分开：

- **断点与结构**在 Views 层：几列、折叠不折叠、显不显示某块 —— 这些是**数量与
  拓扑**，本来就是视图的职责，且官方的六种技术描述的也全是结构变化；
- **外观**仍在 zstyle：小断点的 banner 更矮、导航折叠后变顶栏，都走**分类名**
  （`.banner.compact` / `.nav.collapsed`…），值由样式表给。

这与既有 `.mica` 的做法同构：视图层表达意图，样式层给外观。

## 8. 高度方向为什么还没动（**明确的能力缺口 + 记账**）

宽度方向现在是真自适应的：根容器不再写尺寸、`body` 加 `cross-align: stretch`、
内容卡的 `width` 删掉、窄窗口导航折叠。实测四个尺寸（1400×800 / 1882×953 /
982×653 / 602×853）右侧与内容区都正确铺满。

**高度**不行，原因单一而硬：

> core 的 `Stack::arrange` 只对**交叉轴**施加 `cross_align`，主轴方向没有任何
> "占用剩余空间" 的语义 —— 没有 flex-grow、没有星号行、没有 `Height="*"`。

于是 `window`（垂直 StackPanel）的第二个子项 `body` 的高度只能由**内容**决定，
而"把 body 推到剩满 753" 没有表达方式。要真正跟随窗口高，需要给 core 补：

| 补什么 | 语义 | 两趟各自怎么变 |
|---|---|---|
| 主轴 fill | `Grid` 的 `*` 行 / WPF 的 `Height="*"` | **measure**：fill 子项对内容尺寸贡献 0（它不要固定空间）；**arrange**：主轴剩余空间按 fill 权重分配 |

`measure` 那一步是坑：fill 子项有内容（卡片网格很高），若 measure 返回内容高，
父容器就会按内容定尺寸而把 fill 语义抵消掉。所以两趟都要改，且**每处 `Stack::arrange`
的调用点都是回归面**。

### 这一轮刻意没做的三件事

1. **没有用 `props::HEIGHT` / `props::WIDTH` 在 shell.rs 里按视口下发**。
   试过，被两条自有门禁当场拦下：`the_whole_tree_writes_no_appearance_in_source`
   与 `only_fill_nodes_carry_local_width`。后者的注释写着答案 ——
   「黑名单会烂，**形状**不会」。给 nav 加白名单就是让那条规矩烂掉，
   所以撤回了，改成由 `.nav-pane.compact` 在**样式表**里给窄宽。
2. **没有把 content-card 的 `height: 752` 去掉**。去掉后它的高度由内容决定，
   于是 Home 页的网格会把 body 撑到 1000+，窗口 800 高时溢出更多。
   这是 `MIGRATION.md` §7.4 已为"Home 只能放 10 条"记过的同一笔账：
   core 无滚动 + 无 flex-grow ⇒ 固定高度 + 裁剪，是当时唯一的取舍。
3. **没有同时改布局基准**（见 §5）。响应式与基准换算必须分两轮，
   否则一次改动同时动了「哪套布局」和「布局有多大」，出问题无法归因。

# i18n —— 按浏览器的模型实现，不自己发明规则

> 本轮新增。对应代码：`ZephyraUI/src/i18n.rs`、`ZephyraUI/src/app/mod.rs`（文案表）、
> `zephyra-base/zephyra-platform-win/src/locale.rs`（Windows 取系统语言）。
> 门禁：`ZephyraUI/tests/i18n_tests.rs`（11 条）、`i18n.rs` 内 8 条单测。

---

## 1. 参考对象：浏览器，不是规范书

用户要求「参考浏览器怎么做」。所以本轮**不**去查 W3C/i18n 规范，而是查浏览器
实际行为，然后把它的四条骨架照抄过来。出处与原文：

| 浏览器机制 | 原文 | 本仓对应 |
|---|---|---|
| `navigator.languages` | "an array of strings representing the user's preferred languages. The language is described using a **BCP 47 language tag**. In the returned array they are **ordered by preference** with the most preferred language first." | [`Preferences`](../../ZephyraUI/src/i18n.rs) |
| `Accept-Language` 的 `q` 值 | "generally lists the same locales as the `navigator.languages` property, with **decreasing `q` values**" | [`Preferences::with_weight`] |
| language-only 回退项 | 浏览器会**额外**追加 language-only 标签并给较低 `q`（例：`en-US,en;q=0.9`） | [`Tag::language_only`] + [`Messages::select`] 的第二档 |
| `Intl` 的匹配 | "**the first entry in the list that matches** a locale supported by `Intl` is used" | [`negotiate`] |

出处：<https://developer.mozilla.org/en-US/docs/Web/API/Navigator/languages>
（2026-10 查，含 `Accept-Language` 与 `Intl` 的交叉引用）。

### 1.1 为什么照抄这四条就够

浏览器的 i18n 看着复杂，但**真正决定"用户看到什么"的只有这四步**：

1. 拿一个**有序**的语言标签表（不是单个语言）；
2. 拿一个**可用**的语言表；
3. 按 (1) 的顺序逐个去 (2) 里找**第一个**匹配的；
4. 找不到就用默认值。

剩下的（复数规则、日期格式、`Intl.NumberFormat`）都是**格式化**，不是**选择**。
本仓只做选择，见 §4。

## 2. 回退链：四档，每档都有出处

```
请求标签  →  ① 精确 locale   ② 仅语言段   ③ 默认语言（同样两档）   ④ 键名
```

### 2.1 为什么 `Tag::distance` 的优先级是这个顺序

[`Tag::distance`] 返回 `0 / 2 / 3`，`None` 表示不匹配：

| 情形 | 距离 | 例 |
|---|---|---|
| 三段全中 | 0 | `zh-Hans-CN` ↔ `zh-Hans-CN` |
| 丢 region | 2 | `zh-Hans-CN` ↔ `zh-Hans` |
| 请求缺 script/region | 3 | `zh-TW` ↔ `zh-Hans` |
| 语言段不同 | `None` | `zh` ↔ `en` |
| script 不同（都写明了） | `None` | `zh-Hans` ↔ `zh-Hant` |

最后一行是**故意的**：`Hans` / `Hant` 是两种文字，把它们并成 `zh` 就是在
"给繁体用户看简体"。这与浏览器一致 —— 浏览器对写明了 script 的标签也不合并。

### 2.2 `negotiate` 为什么不是"取全局最接近"

`Intl` 的措辞是 "**the first entry in the list that matches**"。所以：

- 用户把 `ja` 排第一、`en-US` 排第二时，即使 `en-US` 与某个可用项**完全相等**
  （距离 0），也必须先让 `ja` 有机会匹配。
- 这意味着**偏好顺序比匹配精度更重要**。违反它会导致"把日语放在第一位却被忽略"。

门禁 `协商按偏好顺序而不是全局最近` 钉住这一条（`i18n.rs` 单测）。

### 2.3 为什么 `negotiate` 匹配不到时返回 `None` 而不是默认语言

浏览器里"回落默认值"和"在可用表里找"是**同一件事**（`supported locales`
本身就是那份回落表）。本仓把它拆成两步，于是必须分别测：

- [`negotiate`] 答的是"用户偏好里有没有可用的"，没有就返回 `None`；
- 回落默认是**应用层**的一步（[`Gallery::pick_initial_language`] 取 `SUPPORTED[0]`）。

好处是"读不到系统语言"与"没有可用语言"这两种降级在代码里是**不同分支**，
可以分别记账、分别测。代价是多一次调用 —— 那不是热路径（一帧一次）。

## 3. Windows 上从哪读（查过官方文档才写）

### 3.1 `GetUserPreferredUILanguages`

> Retrieves the **thread's preferred UI languages** … The function returns a
> **double null-terminated** list of language names.
>
> —— <https://learn.microsoft.com/windows/win32/api/winnls/nf-winnls-getuserpreferreduilanguages>

三个细节直接决定了实现：

1. 是"**线程的首选 UI 语言**"，**有序** —— 与 `navigator.languages` 同形；
2. **双 null 结尾**的多字符串 → 解析按"连续两个 `\0`"结束，**不是**按分隔符切
   （按分隔符切会在空项上切出空串，而空串会被当成一个"语言"传出去，
   最终在协商里匹配不到任何东西）；
3. `MUI_LANGUAGE_NAME = 0x4`。⚠️ 传 `0`（`MUI_LANGUAGE_ID`）会得到 **LCID 的十进制串**
   （`1033`），而 `1033` 不是 BCP 47 标签 ⇒ 协商**全部落空且不报错**。
   门禁 `标志位必须钉住` 就是这个坑的护栏。

签名是**自声明**的（`windows` crate 未绑定该函数），与 `version.rs` 的 `RtlGetVersion`
同一手法：自己声明 + 一条真机测试钉住「调用真的成功且返回非空」。
签名写错不会编译失败，而是静默返回空表，而那与"成功但无结果"长得一样。

### 3.2 为什么不选别的 API

| API | 为什么不用 |
|---|---|
| `GetSystemDefaultUILanguage` | 只给**一个** LCID，而且是**系统安装**语言，不是用户偏好。用它会把"系统装了什么"当成"用户想用什么"，在中文系统 + 英文界面上直接给错。 |
| `GetUserDefaultLocaleName` | 区域（`zh-CN`）不是语言（`zh`）。用户偏好语言与区域格式是两个设置。 |
| `RegGetValue` 读 `HKCU\...\International` | 是区域格式的注册表位置，且值是 `zh-CN` 这种**区域**标签。 |
| `GetLocaleInfoEx` | 拿的是"当前线程生效的 locale"，而应用启动时线程 locale 可能已经被改过。 |

### 3.3 读一次就缓存

宿主在 [`HostState::new`] 里问一次，存进 `system_languages`，每帧 clone 进
`InputState.languages`。理由：它是**启动时的外部事实**，之后不变
（用户切换系统语言需要重启进程才该重新读）。与版本号、系统主题同一手法。

## 4. 明确**不做**的，以及为什么

| 没做 | 理由 |
|---|---|
| **CLDR 复数规则**（zero/one/two/few/many/other） | 那需要按语言的**选择规则与关键词表**，是**数据**不是逻辑。硬编码"英文式 one/other"会静默给错中文（`other`）与俄文（one/few/many 三档），而**无声的错误比没有更糟**。[`Messages`] 留了 `select` 这个槽位，规则数据不进来。 |
| **日期 / 数字 / 复数格式化** | 官方例子里用的是 `Intl.DateTimeFormat`，那是 ICU。核心仓库引入 ICU 是另一个量级的决定，本轮不做。 |
| **运行期加载 / 按需分块** | 浏览器按 `Accept-Language` 取对应资源文件；本仓的消息表是**编译期常量**（见 §5），`view()` 每帧重建，泄漏不起（`element.rs` 已有这条记录）。 |
| **RTL / `dir` 属性** | 官方断点文档说 RTL 要按语言/地区动态判断。本仓没有方向相关的布局（`spacing` 不分轴、无 start/end 对齐），所以 RTL 只能是空操作 —— 记在 [`responsive.rs`] 的债务里。 |
| **复数 / 参数化插值** | 本仓的文案没有带变量的句子（`"62"` 之类的数值是控件自己拼的）。加一个 ICU MessageFormat 的子集不如不加。 |

**判据统一**：i18n 里"做了一半"的代价（给错复数、RTL 半翻）远高于"不做"。

## 5. 文案表：为什么是一张平表

[`CATALOG`] 是 `&[(&str, &str, &str)]`，不是 `HashMap<locale, HashMap<key, value>>`。

**两种都能取值**，选平表的唯一理由：i18n 唯一真正危险的东西是**漏翻**
（其余问题最多是显示难看）。平表让"门禁枚举漏翻"变成一行
`CATALOG.iter()`；分桶则要 `for locale in SUPPORTED { sheet.get(locale) }`
再加一个"每桶的键集合应当相等"的断言 —— 而那条断言本身就是平表免费的。

分语言分文件是**将来**运行期加载时才需要的形态（§4 已排除）。

### 5.1 值是 `&'static str` 而不是 `String`

`view()` **每帧重建**整棵树。任何运行期构造的字符串都会变成每帧一次分配 +
一次 `Box::leak`（永久泄漏）。而翻译在编译期就定好了 —— 它**不是**运行期数据。
所以：

```
CATALOG &'static str  →  Messages::select -> &'static str
                       →  PropertyValue::static_str  →  属性系统零分配
```

`PropertyValue` 为此专门有一个 `StaticStr` 变体（`property.rs`），其注释明说
"与 `Str` 分开是因为后者持 `Arc`，无法作为 `const` 默认值"。整条路一致。

### 5.2 语言自称（`LANG_SELFS`）**故意不进表**

`"English" / "中文" / "日本語"` 对任何语言的用户都是同一组 —— 它们是**自称**，
不是翻译。放进表里要填 3×3 = 9 条两两相同的内容，而那 9 条迟早会被误改成
"翻译"，而那正是错的。

用**自称**而不是标签或英文名（`en` / `zh-Hans` / "Japanese"）也是通行做法：
一个法国人看不懂 `zh-Hans`，但看得懂"日本語"。

下标对齐由门禁 `语言自称与支持列表等长` 钉住 —— 错位的症状是"选了中文得到日文"，
画面上完全看不出原因。

## 6. 记账：繁体（`zh-Hant`）的缺口

**实测结论**：`zh-TW` / `zh-HK` / `zh-MO` 的用户会拿到**简体**文案。

不是 bug，是真实的产品取舍：`Tag::distance` 把"请求里缺 script"当通配（距离 3），
所以 `zh-TW` 匹配到唯一的 `zh-Hans`。若请求写明了 script（`zh-Hant-TW`）则
**正确地不匹配**，落回默认 `en`（门禁 `回退距离按官方顺序` 钉住这一条）。

浏览器在这里的行为是 `zh-TW` → `zh`（而不是某一种 Hans/Hant），因为浏览器有
likely-subtags 数据库把无 script 的标签补全。本仓**没有**那张表。

**补法**：往 `SUPPORTED` 加 `zh-Hant` 并填一份繁体文案（+26 条）。这是纯数据工作，
不需要改任何代码 —— 本轮不做是因为它会让文案表翻倍，而 demo 的重点不是翻译量。

## 7. 记账：核心层的 `DisplayList` **不含文字**

**实测**：切语言前后 core 的 `DisplayList` **逐字节相同**（6132 字符 vs 6132 字符，
逐位比对相等）。

原因不是 i18n 没接上：

1. `Command::Text` 在 core 的 `render` 里带的是**空字形** —— 字形整形是宿主的活
   （`paint.rs`：`glyphs: Vec<GlyphQuad>`，注释明说"核心不参与字形整形"）；
2. 外壳布局宽度固定（`.nav-pane` 写死 240），文案变长也不引发重排位移。

**影响**：语言差异在核心层**不可见**。能看到的地方只有两处：

1. 保留树上的 `TEXT` 属性 —— 门禁断言的就是它（`系统偏好中文则界面是中文`、
   `手动切语言会换掉画面文字`）；
2. 宿主的字形层 —— 真机上可见。本机 D3D12 资源创建不可用
   （`tests/d3d12_draw.rs` 头部有证据），所以门禁只能走到第 1 层。

门禁 `切语言会让整帧重画` 断言的是"整帧被标记为 `Updated`"而不是
"渲染产物变了" —— 前者可测且有意义（那正是 `frame.rs` 的重排/重绘判据），
后者在核心层**恒假**，一条恒假的断言比没有断言更糟。

## 8. 踩坑记录

1. **`InputState` 加字段会在三个地方编译失败**，而这正是想要的：
   `zephyra-winit-d3d12`（填真值）、`zephyra-winit`（D3D11 后端，填空表）、
   `interaction_tests.rs`（填空表好让断言与宿主机器的 Windows 语言无关）。
   漏填是编译错误，而"填成英语"是行为变更 —— 后者要等到有人在这台机器上用
   中文系统跑起来才会被发现。

2. **`Gallery::on_input` 里协商只能做一次**，判据是 `prefs.is_empty()`。
   手动切语言只改 `lang`、不改 `prefs` —— 若改 `prefs`，再收到一次输入就把
   手动选择冲掉了。症状是"切了语言，下一帧又跳回去"。

3. **`checked` 的初值是 `[true, false, false]`**，所以"点一下"是**取消勾选**。
   断言写成"点完仍是 true"会红，而那与要测的东西毫无关系 —— 写断言前先读默认值。

4. **夹具里 `on_input` 必须在建树之前**。反过来的话保留树是协商前的英文树，
   而断言读的正是它 —— 于是"协商到中文"看到英文，**且看不出是夹具错了**。

5. **门禁里不要用 `DisplayList` 找文案**（见 §7）。要读文字就读保留树的 `TEXT`。

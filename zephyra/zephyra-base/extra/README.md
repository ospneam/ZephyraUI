//! `extra`：**不是所有项目都需要**的系统适配包，独立于主线，按 feature 选择性编译。
//!
//! # 与 `../extra`（core 侧）的分工
//!
//! | | core 侧 extra | 本目录（base 侧 extra） |
//! |---|---|---|
//! | 能碰 unsafe | **不能**（core 的 `forbid` 延伸过来） | 能 |
//! | 能碰平台 API | 不能 | 能 |
//! | 典型内容 | 纯算法（缓动、路径数学） | 设备能力、GPU 后端扩展、系统集成 |
//!
//! 判据与 `zephyra-base/README.md` 的分层判据同源：**能不能在无 GPU、无窗口的
//! 机器上写单测**。能 ⇒ core 侧 extra；不能（必须与系统打交道）⇒ 本目录。
//!
//! # 为什么单独一层，而不是直接加进 `zephyra-winit-d3d12`
//!
//! 那三个后端 crate 是**互不依赖**的（README「为什么 D3D11 与 D3D12 要分 crate」：
//! 两套 API 的词汇混进一处后，「画面一空时是哪个后端的问题」就没法回答）。
//! 而折射、毛玻璃这类能力**天然要碰三个后端** —— 放进任一个 crate 就得让另外
//! 两个反向依赖它，那正是被拆开的原因。
//!
//! 所以它住在**三者之外**：一个可选 crate，被各后端**依赖**（而不是它们互依）。
//! 这样「某个能力三后端都支持」与「某个后端独有一项能力」都能表达，且都不破坏隔离。
//!
//! # 加一个包的规矩
//!
//! 1. 一个包一个 crate，放本目录；
//! 2. `default = []` —— **默认一个 feature 都不开**；
//! 3. 不进 workspace `default-members`（无差别的 `cargo build` 不该编到它）；
//! 4. 要单测的纯逻辑放在自己的 `tests/`，**不要**用需要真窗口/真 GPU 的套件。
